# 蒲公英达人选号（代号 `pgy`）

> 面向**小红书蒲公英平台**（`pgy.xiaohongshu.com`）的 Windows 本地**达人筛选与导出**工具。
> 按给定的检索词（可选一级/二级行业）自动检索达人 → 采集字段 → 产出
> **客户提报表格式的 Excel**（11 列，一人一行）。

形态与姊妹项目 `project2-offical`（Ling 投放助手）**刻意保持一致**：

```
一个可安装的独立 EXE  ＋  一个可挂进 WorkBuddy 的 MCP 连接器
                      ↑
        两者共用同一个本地业务内核；
        不装 WorkBuddy 也能独立使用，装上 WorkBuddy 就能用自然语言驱动。
```

> **当前状态（2026-10-13）**：主链路已跑通，出过经**真机验收**的交付物；
> 安装包在 `release\`（**刻意不入库**，见 `.gitignore`）。
> 本文只描述**稳定的定位与边界**；逐版变化见 [`CHANGELOG.md`](CHANGELOG.md)，
> 实测结论与待验证项见 [`findings.md`](findings.md) —— 这两份是跟着改动走的。
>
> 阅读时仍请严格区分：**规划 → 代码存在 → 自动化通过 → 装机验收 → 真实平台验收**。
> 这五档之间没有任何自动推导关系。

## 一、业务定位

**这是一条「垂直采集成品流水线」，不是通用爬虫平台。**

流程由产品方做死（仅筛选条件、字段、输出模板可配置），第一任务是
**「给定选号需求 → 交付出可用的达人名单」** 这一条链路本身。

| 项 | 说明 |
|---|---|
| 运行形态 | 纯本机单机版，**无服务端**；账号凭据与采集结果只留在本机 |
| 平台范围 | 只有蒲公英，且限定**精确域名** `pgy.xiaohongshu.com` |
| 平台动作 | **只读，且不涉及投放**。不发起邀约、不建合作、不评论、不私信，也不做任何广告投放 |
| 浏览器边界 | **只借用，不接管**——复用登录态，不动用户窗口 / 页签 / Cookie |
| 人工在回路 | 登录、人机验证一律由人完成，程序不绕过任何风控 |
| 数据边界 | 只采集蒲公英页面上**已对资质账号可见**的达人公开信息 |

### 一次选号任务的全貌

> 依据客户提供的真实材料（`资料和说明/`，不入库）。完整规格见
> [`docs/05-业务规则与交付物规格.md`](docs/05-业务规则与交付物规格.md)。

```
客户给需求：检索词（如 体验 / 亲子达人 / vlog…），每个量级要 N 个达人
   ↓
按粉丝量分六个档位（40w-50w … 1w-5w）→ 得各档报价上限（该档基准价 × 1.3）
   ↓
在蒲公英**按档位逐个问平台**：带上这一档的粉丝区间 + 一个检索词
   （可选一级/二级行业；一个请求只能带一个检索词，多词逐个搜再合并去重）
   ↓
本地两道把关：粉丝档位 + 报价上限   ← 平台侧已经挡掉大部分，这两道是兜底
   ↓
按客户表头格式渲染 Excel（一人一行，11 列）
   ↓
导出到设置里指定的目录（默认安装目录下的 `exports\`）
```

**核心特征：报价上限是阶梯，不是单一数值。** 平台报价上限 = 对应粉丝档位的公司基准价 × 1.3，
所以「筛什么价」必须**按粉丝量分档逐段设上限**。生效范围 **粉丝 1w–50w**（KOC 档已排除）。

**「每个量级必凑满 N」是硬性要求**，为此有两处专门设计（细节见 `findings.md` F-40/F-41）：

- 档位带**自己的粉丝区间**去问平台 —— 不带区间时平台按综合排序返回各种粉丝量的人，
  高量级在里面稀疏，超头部那几档永远靠碰运气；
- 某档光靠检索词凑不满（实测 40w-50w 挂上词后整档只剩几十人）⇒ **丢开检索词、
  按这一档的区间再翻一遍**补满。⚠️ **这样补进来的人不保证命中检索词**，界面上会标出来。
  确实一整档都没更多人时，才如实交少。

**中位数是"采集并展示"的字段，不是收录条件**（2026-10-13 起）：曝光/互动中位数照样进表，
但**不参与**"进不进名单"的判定，也从来不参与排序。

**交付物 = 客户提报表，11 列**：
`量级 / 序号 / 昵称 / 粉丝量 / 主页链接 / IP / 类型 / 曝光中位数 / 互动中位数 / 图文 / 视频`

其中字段来源三分：🟢 采集 9 个、🔷 派生 1 个（`量级` ← `粉丝量` + 档位表）、⬜ 自有 1 个（`序号`）。

**筛选条件目前是"一次一填"**（检索词 + 可选一级/二级行业 + 每档条数），
还没有保存 / 命名 / 复跑 —— 那是规划里的 `FilterSpec` / `Task` / `Artifact`
（见 [`docs/03-基础设计说明书.md`](docs/03-基础设计说明书.md)），⏳ 尚未实现。

**档位价格走不入库的配置文件**（`<数据目录>/pricing.json` 或开发期的
`资料和说明/报价档位.json`，格式样板见 `pricing.example.json`）。
⚠️ 拿不到配置时**预算把关会整体关闭**（超预算的达人照样进名单），界面上会明确告警。

## 三、关键设计约束（红线）

以下六条是与姊妹项目一脉相承的硬约束，任何设计不得越过：

1. **平台只读，与投放无关。** 本产品是**数据采集工具**——对蒲公英只有读，没有写，
   也完全不涉及投放。不存在「批量邀约」「建合作」这类功能，也不接受后续以开关形式加进来。
   没有平台写操作，就没有误发/误投的风险，这是本项目风险面小于姊妹项目 Ling 的根本原因。
2. **浏览器只借用，不接管。** 关闭客户端 = 只结束自动化接管；用户的浏览器窗口、页签、登录态一个都不许动。
3. **人机验证与登录由人完成。** 程序不实现任何验证码识别 / 绕过 / 打码。撞上验证就停下等人。
4. **抓取必须节流。** 采集是高频动作，比投放更需要限速与退避。严禁并发轰炸、严禁绕过平台频率限制。
5. **凭据只进 Windows 凭据管理器。** 绝不明文写入 SQLite / JSON / 日志 / 源码；任何接口都不返回密码。
6. **MCP 是薄客户端。** 业务逻辑只存在于 `backend/`。MCP 层只做「拼 URL、翻译错误、转发调用」，不在 MCP 里复制一份业务判断。

## 四、技术栈（已落地）

| 层 | 选型 | 备注 |
|---|---|---|
| 桌面壳 | **Tauri 2**（Rust） | NSIS 装包，`externalBin` 带 sidecar |
| 前端 | React 19 + TypeScript + Vite + Tailwind + TanStack Query/Router | 选号页 / 账户页 / 设置页（`zustand` 在依赖里但无人引用） |
| 业务内核 | **Python + FastAPI + uvicorn**（`pgy-backend.exe`，PyInstaller onefile） | 只听 `127.0.0.1:18081`；**唯一业务内核**，前端与 MCP 都是薄客户端 |
| 浏览器自动化 | **Playwright**（程序托管内核） | 复用登录态，全程可见 |
| 本地存储 | **文件**：`settings.json` / `selection-cursor.json` / `pricing.json` | ⚠️ SQLite **实际没在用**：骨架遗留的 `backend/db/mio_db.py` 目前无人引用 |
| 导出渲染 | **openpyxl** | 只有一张表（客户 11 列表头）。**图片榜单未做**（待确认项 D5） |
| MCP 连接器 | Python stdio 服务（`pgy-mcp.exe`，PyInstaller） | 独立安装，注册进 WorkBuddy 的 `mcp.json`（装法见 `pgy_mcp/安装说明.md`） |
| 打包 | `build-sidecar.ps1` → `build-mcp.ps1` → `build-installer.ps1` | 与参考项目同一条链路；版本号四处一致校验见 `build/bump-version.ps1` |

> **端口刻意避开参考项目：** Ling 用 `18080`，本项目用 **`18081`**。
> 两者可能装在同一台机器（同一投放团队同时用），端口与数据目录都必须隔离。

| | Ling 投放助手 | 蒲公英达人选号 |
